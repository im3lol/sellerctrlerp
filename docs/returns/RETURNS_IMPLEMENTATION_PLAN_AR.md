# خطة تنفيذ دورة المرتجعات والمبالغ المستردة والتعويضات

**الإصدار:** 1.0 — **التاريخ:** 15 نوفمبر 2026 — **الحالة:** مسودة للاعتماد قبل التنفيذ.

هذه الخطة تخص SellerCtrl الحالي. إعدادها لا يغيّر كود التطبيق أو قاعدة البيانات أو إعدادات الإنتاج، ولا يعتمد أو ينفذ أي تسوية تاريخية. الهدف أن يصبح لكل مبلغ وكمية مصدر وإثبات ومستند وحالة معالجة ومسؤول اعتماد.

## 1. النطاق وقواعد لا يجوز تجاوزها

1. البداية بتكامل Amazon FBA وFBM/MFN، مع تصميم قابل لإضافة المنصات الأخرى دون تكرار محركات القيود والمخزون.
2. ملف متابعة واحد للمرتجع، يدعم عدة بنود وأحداث وردود مبالغ واستلامات وتوزيعات جزئية. رقم الطلب وحده ليس هوية كافية.
3. استقلال رد المبلغ عن رجوع البضاعة، واستقلالهما عن تعويض Amazon وتحرير رصيد المنصة والتحويل البنكي.
4. بيانات المصدر الأصلية محفوظة؛ قرار المستخدم لا يستبدل حالة Amazon أو مبلغها أو الكمية المبلّغ عنها.
5. استيراد الحدث ليس ترحيلًا محاسبيًا. المطابقة ليست اعتمادًا. اعتماد مرحلة لا يغلق المراحل الأخرى تلقائيًا.
6. الاعتماد اليدوي هو الوضع الافتراضي. أي أتمتة لاحقة تكون لكل مؤسسة ونوع حدث، بعد نجاح المطابقة والاختبارات واعتماد سياسة مستقلة.
7. لا إصدار Refund جديد إلى Amazon في هذا المشروع. المزامنة تقرأ وتطابق ما حدث. إدارة المطالبة تشمل ملفها وأدلتها وتسجيل تقديمها ومتابعتها؛ تقديمها آليًا لا يدخل النطاق دون إثبات وجود واجهة رسمية مناسبة للحساب والسوق واعتماد منفصل.
8. لا إعادة كتابة لمستند مُرحّل. التصحيح بمستند عكسي/تسوية موثقة، مع احترام الفترات المقفلة.
9. لا تعديل تلقائي للأرصدة التاريخية أو تنفيذ لكشف التسويات السابق. لا مسح للأدلة عند تعطيل الميزة.

## 2. مصفوفة الحالات الواجب دعمها

| الحالة | الحركة المالية | حركة البضاعة المطلوبة | المتابعة والإقفال |
|---|---|---|---|
| طلب إرجاع دون Refund أو استلام | لا نفترض رد مبلغ | انتظار/تتبع | مفتوح، دون قيد أو زيادة مخزون افتراضية |
| Refund قبل وصول البضاعة | تسجيل ومطابقة المبلغ الفعلي | انتظار الرجوع إن كان مطلوبًا | المالي مستقل، المخزني معلق |
| وصول البضاعة قبل Refund | لا نفترض رد مبلغ | استلام وفحص بالكمية المثبتة | المخزون مستقل، المالي معلق أو غير مطلوب بمصدر |
| FBA رجع صالحًا لمركز Amazon | وفق الحدث المالي الحقيقي | استعادة في مخزن FBA المرتبط | لا يشترط وصوله لمخزن التاجر |
| FBA رجع غير صالح للبيع | وفق الحدث المالي الحقيقي | عزل/تقييم، لا إتاحة تلقائية للبيع | تصرف موثق أو نقل/شطب معتمد |
| العميل أعاد المنتج مباشرة للتاجر | وفق رد المبلغ الفعلي/القرار المعتمد | إذن استلام وفحص بالمخزن المحدد | الكمية والتكلفة مرتبطتان بالأصل |
| Amazon شحنت البضاعة للتاجر | ليست عملية بيع أو Refund جديدًا | خروج FBA، مخزون بالطريق، ثم استلام | نقل ملكية المكان لنفس الكمية دون مضاعفة الأصول |
| شحنة الإزالة وصلت ناقصة | لا نغيّر Refund العميل | المستلم فقط يدخل الوجهة | الباقي بالطريق/استثناء ومطالبة محتملة |
| Refund لثلاث قطع ووصول قطعتين | يظل رد الثلاثة كما حدث | يدخل قطعتان فقط | الثالثة تبقى معلقة حسب سببها |
| Refund جزئي بالقيمة دون كمية معلومة | مبلغ معلوم وكمية غير معلومة | لا نستنتج كمية من السعر | مطابقة/قرار خاص، دون حركة مخزون مخمّنة |
| Refund بدون اشتراط رجوع المنتج | مبلغ فعلي مثبت | لا استلام ولا استعادة تكلفة بضاعة | «لا يلزم إرجاع» بدليل/قرار، والتعويض ليس مضمونًا |
| منتج غير قابل للإرجاع وفق سياسة البيع | لا أثر مالي تلقائي | لا أثر مخزني تلقائي | يظل وصف سياسة، لا دليلًا أن Refund حدث أو تنازلًا عن الرجوع |
| منتج مطلوب إرجاعه لكنه لم يصل | مطابق لما رُد فعلًا | لا زيادة مخزون | استثناء قابل للمطالبة وفق الأهلية الفعلية |
| منتج مختلف أو صندوق فارغ | مطابق لما رُد فعلًا | حجز الموجود للفحص، دون اعتباره الصنف الأصلي | الأصل يظل غير مستلم؛ إثبات ومطالبة/قرار |
| تالف أو مفقود عند Amazon | لا نفترض تعويضًا | تسوية/إعادة تصنيف وفق الإثبات | لا إعادة تحميل تكلفة أُثبتت سابقًا كمصروف |
| تعويض نقدي جزئي أو كامل | إثبات مستقل ومطابقة مع المحفظة | لا زيادة كمية لمجرد التعويض النقدي | الباقي معلق إن وجد |
| تعويض بمخزون | إثبات معاملة التعويض بالقيمة المعتمدة | زيادة مرة واحدة للكمية الممنوحة فعليًا | لا تسجيل تعويض نقدي لنفس الجزء أيضًا |
| رفض مطالبة أو سحب تعويض سابق | عكس/تسوية موثقة عند الحاجة | مطابقة أثرها إن شمل مخزونًا | سبب وقرار نهائي محفوظان |
| استبدال منتج/إعادة شحن | لا نكرر إيرادًا تلقائيًا | صرف جديد مرتبط بأمر استبدال | منفصل عن استلام الأصل ورد المبلغ |
| إلغاء طلب/شحنة لم تُسلّم أصلًا | حسب المستندات التي اعتُمدت فقط | عكس الصرف إن كان حدث، لا إنشاء مرتجع وهمي | مسار إلغاء/RTO مستقل مرتبط بالطلب |
| تعدد فواتير أو تسليمات أو ردود لنفس الصنف | تخصيص القيمة على أصولها الصحيحة | تخصيص الكمية والتكلفة على تسليماتها | لا اختيار «آخر إذن» ولا دمج بالطلب وSKU وحدهما |
| وصول مستند متأخر بعد إقفال الملف | لا نتجاهل الحدث أو نكرر أثره | مطابقة مع الإقفال السابق | إعادة فتح موثقة/مراجعة إذا تعارضت الأدلة |

## 3. من يثبت الحدث ومن يقرره؟

| الحدث | الإثبات | صاحب الاعتماد | ما لا يُعد إثباتًا |
|---|---|---|---|
| استلام مركز Amazon | مصدر FBA المرتبط ومطابقة حركة المخزون | مسؤول المخزون أو اعتماد آلي مصرح لاحقًا | مجرد وجود Refund أو طلب إرجاع |
| وصول مخزن التاجر | إذن استلام، الفاحص، الوقت، الكمية، الحالة، المخزن والمرفقات | مسؤول مخزن مخوّل | أن Removal Order أصبح shipped |
| رد مبلغ العميل | حدث مالي بمكوناته ومرجعه وعملته، أو سند رد معتمد للمبيعات اليدوية | مسؤول مالي | حالة المنتج أو توقع سعر البيع |
| الاحتفاظ برصيد دائن | قرار مالي واضح مرتبط بالمستند والعميل | مسؤول مالي مخوّل | افتراض أن الرصيد الدائن يعني دفع نقدية |
| تغيير حالة المنتج | فحص أو حالة موثقة من المصدر، مع فصل الجديدة عن المستعملة والمحجوزة | مسؤول مخزون | تسمية عامة «تالف» تُسقط قيمته تلقائيًا للصفر |
| شطب/إعدام | واقعة ومستند وكمية وقيمة وسبب | اعتماد مالي/مخزني وفق السياسة | غياب مخزن للتوالف |
| مطالبة وتعويض | Case ID/دليل تقديم، ثم حدث تعويض ومطابقة | مسؤول المطالبات ثم مسؤول مالي/مخزني | أن المنتج لم يصل فقط |
| إقفال استثناء دون تعويض | قرار مسبب وإقرار بالأثر المالي المتبقي | مدير مخوّل | إخفاء الصف من قائمة العمل |

يمكن للمستخدم تسجيل «لم أستلم». في FBA يظهر له في الوقت نفسه إن كانت Amazon تؤكد الاستلام في مركزها. هذا اختلاف وجهة/إثبات، وليس تعارضًا يُحل بمسح إحدى المعلومتين. الاعتراض على المصدر ينتج حالة مراجعة مع دليل، ولا يعيد المخزون للخلف بصمت.

## 4. مصادر SP-API والتحقق من توافرها

الاختيار التالي تصميم SellerCtrl استنادًا لوظائف المصادر الرسمية، وليس وعدًا بتوفر كل مصدر أو صلاحية بكل حساب وسوق.

| المصدر | وظيفته في التصميم |
|---|---|
| Finances v2024-06-19 / listTransactions | أحداث المال ومكوناتها ومعرفاتها وحالاتها. لا نستخدم صافي المحفظة بدل مبلغ العميل |
| GET_FBA_FULFILLMENT_CUSTOMER_RETURNS_DATA | إثبات رجوع إلى مركز Amazon وحالة الوحدة |
| GET_LEDGER_DETAIL_VIEW_DATA | مرجع لمطابقة حركة المخزون ومكانها وسببها |
| GET_FLAT_FILE_RETURNS_DATA_BY_RETURN_DATE وتقارير Prime المناسبة | بيانات إرجاع الشحن من البائع، RMA وبنود الطلب والتتبع |
| GET_FBA_FULFILLMENT_REMOVAL_ORDER_DETAIL_DATA | تتبع طلب الإزالة والكميات المطلوبة والمنفذة |
| GET_FBA_FULFILLMENT_REMOVAL_SHIPMENT_DETAIL_DATA | بيانات شحنة الإزالة والتتبع؛ الاستلام المحلي يحتاج إثباته الخاص |
| GET_FBA_REIMBURSEMENTS_DATA | تعويضات نقدية/مخزنية ومراجعها، مستقلة عن Refund العميل |

الوثائق تفرق بين FBA وتقارير مرتجعات الشحن من البائع، والأخيرة لا تغطي Returnless Refund. وتنبّه Finances إلى تأخر بعض الأحداث الحديثة. لذلك «لم يظهر بالمزامنة» يختلف عن «لم يحدث». [تقارير FBA](https://developer-docs.amazon/sp-api/docs/report-type-values-fba)، [تقارير المرتجعات](https://developer-docs.amazon/sp-api/docs/report-type-values-returns)، [Finances](https://developer-docs.amazon/sp-api/docs/finances-api-v2024-06-19-reference).

تُختبر صلاحيات الحساب والأسواق ومصادر البيانات الحالية قبل التنفيذ. يظهر لكل مصدر: مدعوم/غير مدعوم/صلاحية ناقصة/متعطل/قديم، وآخر نجاح ونهاية الفترة المكتملة. لا نحول فشل التقرير إلى «صفر مرتجعات». لا تُعرض المطالبة كتقديم تلقائي إن كانت متاحة يدويًا فقط في Seller Central.

## 5. ملف المتابعة وحالاته

كل ملف يربط المؤسسة، حساب البائع، السوق، المنصة، FBA أو MFN، الطلب، بند الطلب، المنتج وأكواده، الشحنات والتسليمات والفواتير الأصلية. يدعم الردود والاستلامات الجزئية بمخصصات مستقلة.

### أ. الاعتماد والمطابقة المالية

`بانتظار البيانات` ← `يحتاج مطابقة` ← `جاهز للاعتماد` ← `إشعار دائن/تسوية معتمدة` ← `مطابق ماليًا`.

المكونات المجهولة أو المتعارضة توقف اعتماد الجزء المختلف. يبقى تمييز مستقل بين رد العميل، قيد المحفظة، DEFERRED/RELEASED، والتحويل البنكي. مطابقة Refund لا تعني أن دفعة البنك وصلت؛ تحويلات البنك تتابع على مستوى دفعة المنصة ولا تفرض تكرار قيود لكل مرتجع.

### ب. الاستلام والتصرف في البضاعة

`غير محدد` / `بانتظار الرجوع` / `بالطريق` / `مستلم جزئيًا` / `مستلم بالكامل`، ثم توزيع المستلم إلى `صالح` أو `محجوز للفحص` أو `غير صالح للبيع كجديد` أو `شطب معتمد`.

يوجد مسار مستقل `لا يلزم إرجاع` بدليل أو اعتماد، ومسار `لم يصل/مختلف/ناقص` كاستثناء. حالة الكمية قابلة للتجزئة: بعض الوحدات مغلق وبعضها مفتوح.

### ج. المطالبة والتعويض

`غير مطلوب` / `للمراجعة` / `جاهز للمطالبة` / `قُدّم` / `معلومات إضافية مطلوبة` / `مقبول جزئيًا` / `مقبول` / `مرفوض` / `تعويض مرصود` / `تمت المطابقة` / `إقفال بقرار`.

وجود مبلغ متوقع لا يثبت مستحقًا محاسبيًا تلقائيًا. التعويض القابل للاعتراف يحتاج شروط السياسة المحاسبية المعتمدة ومصدره. المبلغ المتوقع والمقبول والمرصود والمطابق والناقص حقول مختلفة.

### د. الإقفال العام

يُشتق من البنود والمراحل، ولا يكون خانة يمكن وضعها «مغلق» رغم نقص المتطلبات. تظهر «مغلق ماليًا فقط»، «مغلق مخزنيًا فقط»، «تعويض معلق»، «استثناء»، و«مغلق بالكامل».

الإقفال الكامل يتطلب معالجة كل التزامات الملف المطلوبة، وتسوية كل كمية وقيمة أو إعفاء موثق، وعدم وجود تعارض مصدر أو مطالبة لازمة مفتوحة. لا يلزم إنشاء مطالبة لكل ملف، ولا انتظار تعويض لحالة لا تستحقه أصلًا. السبب والقرار محفوظان عند التنازل أو الرفض.

## 6. قواعد الكميات والتكلفة والمال

### الكميات

- تبقى كمية البيع الأصلية محفوظة. لا نخفضها لإجبار أمر البيع على الظهور «مكتملًا».
- تُفصل كمية Refund إن وردت عن الكمية المطلوب إرجاعها، والكمية المستلمة، والمعفاة من الرجوع، والمعلّقة، والمنقولة، والمشطوبة، والمعوّض عنها.
- مبلغ Refund وحده لا يحدد كمية المنتج. الكمية المجهولة تبقى مجهولة ولا تُستبدل بواحد أو صفر لتسهيل المعالجة.
- لكل التزام إرجاع معلوم: المطلوب = المستلم المعتمد + المتبقي + المعفى المعتمد، مع منع تجاوز التخصيصات.
- لا تُجمع حالة «استُلم» مع تصرف «نُقل» كأنهما قطعتان مختلفتان. المنتج الواحد قد يمر باستلام FBA ثم نقل لمخزن التاجر.
- نقل FBA إلى التاجر يستخدم مرحلة «بالطريق» ونقلًا بالقيمة الدفترية؛ لا شراء أو إيراد أو استعادة تكلفة جديدة بمجرد تغيّر الموقع.
- لا إعادة حجز/صرف بديل تلقائيًا بعد مرتجع. إعادة الشحن عملية جديدة صريحة مرتبطة بملف المرتجع.

### التكلفة

- استرجاع تكلفة الجزء العائد يرتبط بحركة الصرف والدفعة والتوزيع الأصلي، لا بآخر متوسط تكلفة أو آخر حركة للصنف.
- في الشحنات المتعددة أو المخازن المتعددة يلزم توزيع معلوم، وإلا توقف المطابقة للمراجعة.
- المنتج غير الصالح للبيع قد يحتفظ بقيمة. يُحجز ويُقيّم وفق سياسة معتمدة، ولا يُعدم لمجرد عدم اختيار مخزن تالف.
- إن لم ترجع البضاعة، لا نستعيد تكلفتها للمخزون؛ وتكلفة البيع التي سُجلت سابقًا تظل محسوبة. لا نضيف تكلفة القطعة نفسها مرة ثانية باعتبارها خسارة جديدة.
- أي إعادة تصنيف من تكلفة بيع إلى خسائر، أو استلام ثم انخفاض قيمة، يجب أن يحافظ على إجمالي الأثر دون مضاعفة المصروف.
- قيمة المخزون بالأستاذ تطابق سجل المخزون وفق حسابات المؤسسة المعيّنة، بما فيها المخزون المحجوز أو بالطريق وفق الإعداد المعتمد.

### المال والرسوم

- مكونات رد العميل: ثمن البند والخصم والضريبة والشحن وأي مكون مشروع معروف. تُؤخذ من الحدث الأصلي والمستند وتُطابق؛ لا تُخمن من كمية الاستلام.
- رسوم المنصة، رسوم رد المبلغ، رسوم شحن الإرجاع، رسوم الإزالة والرسوم المعادة تُحفظ مستقلة بإشاراتها وتواريخها.
- لا نساوي صافي transaction بعد الرسوم بالمبلغ الذي وصل للعميل.
- لا نعكس كل مصاريف البيع تلقائيًا. المصروف المعاد يُخفض، والمحتفظ به يظل محسوبًا، والمكون غير المطابق يظل استثناءً.
- يُفصل قيد الإشعار الدائن عن تطبيق Refund على رصيد العميل/المنصة؛ كل مصدر له أثر واحد فقط، مع منع تكرار تخفيض المديونية بين مسار المرتجع ومسار التسويات.
- المبيعات اليدوية تدعم رصيدًا دائنًا معتمدًا أو سند رد فعلي مرتبط بالصندوق/البنك. أحدهما لا يثبت الآخر.
- تُحفظ العملة والقيمة الأصلية وسعر الصرف المستخدم والقيمة الأساسية وفروق العملة منفصلة. لا تجمع عملتين دون تحويل معلن.
- يُحفظ الفرق بين تاريخ الحدث وتاريخ وروده وتاريخ الترحيل. الفترة المقفلة لا تُفتح أو تعدل تلقائيًا.
- لا يُستنتج إجمالي الربح بجمع مراحل الدورة؛ الربح المعروض يُطابق القيود المعتمدة، ويكشف أثر المرتجع والرسوم والخسائر والتعويض كلًا على حدة.

## 7. المطابقة ومنع التكرار

ترتيب الأدلة: معرف الحدث الأصلي وروابطه، ثم بند الطلب/الفاتورة والشحنة والتسليم، ثم أكواد المنتج ضمن حساب البائع والسوق والمؤسسة. RMA/LPN/FNSKU تُستخدم عند توافرها. التطابق بالطلب وSKU وحدهما مرشح وليس اعتمادًا نهائيًا عند تعدد الاحتمالات.

1. دعم عدة Refunds لنفس البند، وRefund واحد لعدة بنود، واستلام واحد على عدة أيام.
2. تقييد مخصصات الكمية والقيمة بالمتاح، داخل معاملة مع قفل يمنع السباق بين مستخدمين أو عاملَي مزامنة.
3. ربط إصدارات الحدث وتغير حالاته بمعرفاته وعلاقاته الرسمية؛ لا نفترض أن transactionId أو shipmentId وحده يحل كل حالات التكرار، ولا ندمج حدثين مستقلين لمجرد تساوي المبلغ.
4. وصول التقرير المخزني قبل المالي أو العكس لا ينشئ ملفًا ماليًا ثانيًا لنفس التخصيص.
5. التمييز بين تحديث بيانات المصدر وبين حدث اقتصادي جديد. الاحتفاظ بالمراجعات وإظهار التعارض بعد الاعتماد.
6. لكل اعتماد مفتاح تكرار فريد وروابط ثابتة بالمستندات الناتجة. إعادة الطلب تُرجع نفس النتيجة.
7. المصدر المخزني يُستهلك مرة واحدة: تقرير المرتجع وInventory Ledger إثباتان لنفس الحركة إن تطابقا، وليس سببي زيادة مستقلين.
8. مطابقة Inventory Snapshot تُظهر فروقًا للمراجعة، ولا تنشئ تسوية عامة تكرر أثر مرتجع أو إزالة معالَج.
9. التأكد من حدود الكمية والمبلغ عبر المرتجعات السابقة المعتمدة، مع عدم تحرير تخصيص إلا بعكس موثق. القيم السالبة/العكسية تُعامل كمراجعة أو حدث عكسي معلوم، لا تُحذف.

## 8. نموذج البيانات المقترح

تُعاد الاستفادة من جداول المصادر الحالية ومحركات المستندات. الأسماء التالية مقترحة وتُراجع مع المخطط قبل إنشاء الترحيل:

| الكيان | الحد الأدنى اللازم |
|---|---|
| return_cases | المؤسسة، حساب البائع، السوق، المنصة، طريقة الشحن، الطلب، المسؤول، الحالة المشتقة، التواريخ والإصدار |
| return_case_lines | المنتج وبند الطلب، الكميات/القيم المعروفة، وروابط البنود والفواتير والتسليمات الأصلية |
| return_source_events | المصدر وهوية الحدث ومراجعاته وحالته الأصلية، تاريخ الحدث والوصول، العملة والمكونات والكمية عند معرفتها، مرجع المحتوى الخام |
| return_allocations | تخصيص مقدار من قيمة/كمية حدث إلى بند ومرحلة ومستند، مع حدود الاستهلاك ومراجع العكس |
| return_receipts | إثبات الاستلام والفحص والوجهة وحالة الوحدات والتتبع والمرفقات ومعتمد الاستلام |
| return_claims | نوع المطالبة وسببها وCase ID وحالتها والمبالغ والكميات المتوقعة/المقبولة/المطابقة والأدلة والمواعيد |
| روابط المستندات والقرارات | إعادة استخدام document_links وaudit قدر الإمكان، مع ربط اعتماد المرحلة والإعفاء والتصحيح بالمستخدم والسبب والمرفقات |

الهوية الخارجية نطاقها المؤسسة + حساب البائع + السوق + المصدر. كل الجداول والروابط والمرفقات والمخصصات معزولة بالمؤسسة وRLS وروابط أجنبية متوافقة. الملفات الخاصة بروابط مؤقتة وصلاحيات القراءة المناسبة. لا بيانات عملاء أو أسرار في التقارير العامة أو سجلات التشغيل.

## 9. واجهة الاستخدام والتحكم

قسم واحد «المرتجعات والتعويضات» من المبيعات، وروابط مقابلة من المنصة والفاتورة وأمر البيع والمنتج والمخزن.

قوائم: يحتاج إجراء، بانتظار الرجوع، مغلق ماليًا فقط، مخزني مكتمل، مطالبات، تعويضات، استثناءات، مكتمل. لا تقتصر القائمة على مسودات المستندات.

صفحة الملف تعرض:

- ملخص الطلب والفاتورة وطريقة الشحن والوجهات، مع مؤشرات المالي والمخزني والرسوم والمطالبة.
- جدول البنود والكميات الأصلية والمستلمة والمعلقة والمعفاة والمشطوبة، دون خلط المراحل.
- جدول مالي: مكونات البيع ورد العميل والرسوم المعادة والمحتفظ بها والتعويض، مع تمييز المتوقع من المعتمد والمطابق.
- خط زمني للمصدر وقرارات المستخدم والمستندات، ومن أثبت واعتمد كل خطوة.
- إثباتات FBA وإذن الاستلام المحلي ونتيجة الفحص والشحنة بالطريق والمرفقات.
- أزرار منفصلة: اعتماد الجزء المالي، تسجيل استلام، تسجيل «لم يصل»، عزل/نقل، طلب شطب، تجهيز مطالبة، تسجيل تقديمها، مطابقة تعويض، طلب إعادة فتح.
- معاينة الأثر قبل التأكيد: الكمية والمخزن والتكلفة والقيمة والضريبة والرسوم والمستندات التي ستُنشأ. إعادة تحقق بالخادم وقت الاعتماد.
- صفحة واحدة مناسبة للموبايل، مع فلاتر مختصرة داخل لوحة قابلة للطي، وتفاصيل البنود تدريجيًا.

الخانات لا تُملأ بكمية استلام افتراضية. اختيار «لم يصل» لا يصفر Refund ولا يثبت تعويضًا ولا يقفل الملف. أي تصحيح بعد اعتماد يُنشئ طلب عكس/تسوية، ولا يفتح تعديلًا مباشرًا للمصدر أو المستند.

## 10. الصلاحيات والاعتمادات

تُربط بالإطار الحالي، مع فصل قدرات العرض، المزامنة، المطابقة، الاستلام، اعتماد المال، النقل، الشطب، المطالبة، مطابقة التعويض، الإقفال الاستثنائي والعكس. الأسماء النهائية تُحدد دون كسر أدوار المؤسسات الحالية.

موظف المخزن لا يعتمد ردًا ماليًا لمجرد قدرته على الاستلام. مسؤول مالي لا يثبت استلامًا فعليًا دون الصلاحية والإثبات. المدير يمكن منحه الجمع بين الأدوار، مع فصل منشئ الطلب ومعتمده للحالات التي تختار المؤسسة اشتراط اعتمادين فيها. دخول الأدمن للدعم لا يتجاوز صلاحيات المؤسسة أو سجل الاعتماد.

تطبق الصلاحيات في الصفحة وServer Action والعامل الخلفي وروابط التحميل، وليس بإخفاء الأزرار فقط. إعادة الإرسال بعد تغيير الصلاحية أو المبلغ لا تستخدم معاينة قديمة.

## 11. المزامنة والتشغيل

- استخدام worker والصفوف الحالية، مع أقفال لكل مؤسسة/حساب/مصدر، وحدود طلبات Amazon وإعادة محاولة بتأخير متزايد.
- فصل السحب عن التطبيع عن المطابقة عن إنشاء المسودات عن الاعتماد. لا يبقى اتصال قاعدة مفتوحًا أثناء انتظار تقرير خارجي.
- تتبع pagination حتى النهاية، ونوافذ زمنية صحيحة للمصدر، مع تقسيم المدد الطويلة وإعادة قراءة نوافذ متداخلة للأحداث المتأخرة.
- watermark لا يتقدم إلا بعد اكتمال معالجة الجزء المقصود بنجاح. يُسجل الفشل الجزئي دون الادعاء باكتمال اليوم.
- جدولة حسب حداثة كل مصدر وتوافره وحالة الملفات المفتوحة، لا طلب كل التقارير باستمرار لكل مؤسسة.
- حفظ raw/نسخة تطبيع قابلة للتتبع، مع سياسة احتفاظ وربط آمن بالمرفقات. السجلات العامة تحوي معرفات تشغيل وأكواد خطأ لا محتوى ماليًا خامًا.
- فصل التنبيه عن سياسة الأهلية للمطالبة. مواعيد المطالبات تُضبط وفق السوق والسياسة والمصدر الموثّق؛ لا نفترض مهلة عالمية ثابتة.
- مؤشرات تشغيل: مصادر متأخرة، أحداث غير مرتبطة، تعارضات قيمة/كمية، محاولات مكررة مُنعت، ملفات معلقة بالعمر، فشل الترحيل، تعويض غير مطابق.

## 12. ضمان التنفيذ والمعاملات

كل اعتماد مرحلة ينفذ إنشاء مستنداته وروابط المصدر والمخصصات وحالة المرحلة وسجل التدقيق داخل معاملة ذرية واحدة. الخطأ يُجهضها؛ إرجاع `{error}` من وسط معاملة لا يُعتبر rollback تلقائيًا.

الأحداث التي حدثت خارج النظام لا تتراجع بفشل مرحلة أخرى: Refund مثبت يظل حدثًا محفوظًا، ويُعاد اعتماد آثاره المحلية بأمان. يمكن أن يكتمل المالي ويبقى المخزون معلقًا، لكن لا تبقى نصف مستندات اعتماد مالي واحد. الاستئناف يعتمد على مراجع محفوظة وقيود فريدة، لا إعادة إنشاء عمياء.

تحديث ملف واحد بالتزامن يحتاج قفل/إصدار ومراجعة رصيد التخصيص داخل المعاملة. تُستخدم محركات postEntry وpostStockMovement الحالية بعد تزويدها بالأصل الصحيح، دون SQL حر أو كتابة مباشرة تتجاوز ضوابطها.

## 14. خطة الترحيل والبيانات القديمة

1. نسخة احتياطية واختبار استعادة على بيئة معزولة قبل أي ترحيل إنتاج لاحق.
2. ترحيل إضافي وفهارس مناسبة، مع اختبار أثر الأقفال والحجم قبل التفعيل. لا إعادة تطبيق شاملة لسياسات الإنتاج دون خطة.
3. استيراد تاريخي للمراقبة فقط لفترة تُختار صراحة، مع حفظ نقطة البداية وحدود الاكتمال.
4. ربط المستندات القديمة الواضحة بعد معاينة، وتمييز «ملف قديم يحتاج مراجعة» للحالات الغامضة؛ لا إنشاء Refund أو حركة مخزون تعويضية آليًا.
5. منع المسارين القديم والجديد من الكتابة لنفس النطاق الزمني/نوع الحدث. سحب المصدر لا يتوقف، لكن كاتب المستندات واحد.
6. مقارنة أعداد وقيم ومكونات وكميات، مع تقرير اختلافات قبل التفعيل وبعده.
7. التراجع يعطل الاعتماد الجديد ويعيد التوجيه الآمن دون حذف سجل الأحداث أو إعادة تشغيل كاتب قديم يكرر ما عالجه الجديد. الآثار المُرحّلة تُعكس بمستندات عند الضرورة، لا بإسقاط الجداول.

## 15. اختبارات القبول المطلوبة

كل سيناريو في القسم 2 له اختبار، ويضاف إليها:

- ضغط الاعتماد مرتين، طلب متزامن من مستخدمين، وإعادة تشغيل worker بعد فشل/انقطاع.
- وصول الملف المالي أولًا، والمخزني أولًا، والتقريرين معًا، ثم إعادة نفس البيانات.
- أكثر من Refund لنفس SKU والطلب بنفس اليوم، بما فيها مبالغ متساوية لأحداث مختلفة.
- تحديث الحالة ومعرفات الحدث ومراجع تحريره، دون ضياع التحديث أو تكرار القيد.
- تعطل مصدر أو انتهاء الصلاحية أو صفحة فارغة مع nextToken؛ لا إقفال ولا watermark زائف.
- بنود بضريبة وخصومات وشحن مختلفين، ورد جزئي بالقيمة، وتقريب القروش عبر دفعات.
- فاتورة مدفوعة/مدفوعة جزئيًا، ورصيد دائن، وسند رد فعلي، وعكس المرتجع.
- أصل تكلفة متعدد الدفعات والمخازن، ونقل بالطريق، وتالف جزئي، وتعويض مخزني يتبعه استلام متأخر للأصل.
- منع عكس رد العميل مرتين بين الإشعار الدائن والتسويات؛ مطابقة الذمم والمحفظة والرسوم مع الأستاذ.
- أحداث بلا فاتورة محلية، أو طلب سابق لتاريخ التشغيل، أو SKU غير مرتبط: ملفات استثناء لا فواتير مخمّنة.
- فروق عملة وفترة مقفلة ومستند مصدر عُدّل بعد اعتماد محلي.
- مؤسسة أخرى، تبديل حساب البائع/السوق، IDOR بالمرفقات والمخازن والفواتير، صلاحية سُحبت بعد المعاينة، وتسرب سياق من تجمع الاتصالات.
- الشاشة وExcel والطباعة والموبايل تعطي نفس أرقام البيانات المعتمدة، مع فلاتر وفترات معلنة.
- كل ملف مغلق يمكن تتبع كمياته وقيمه لمصادر ومستندات وقرارات. لا ملف مغلق وله مخصصات متجاوزة أو متطلبات مجهولة.

بوابات النجاح: اختبارات عزل وتزامن ناجحة؛ تطابق مبالغ وكميات حسب دقتها، والقيود متوازنة؛ لا أثر مالي/مخزني مضاعف؛ لا ملفات قديمة صُححت دون اعتماد؛ استمرار دورة البيع الحالية دون تغيير غير مقصود.
