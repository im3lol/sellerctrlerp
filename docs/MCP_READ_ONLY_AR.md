# ربط المساعد الشخصي بـSellerCtrl

الإصدار الأول: MCP عبر Streamable HTTP مع OAuth Authorization Code وPKCE S256، للقراءة والتحليل فقط. يستعمل SDK الرسمي @modelcontextprotocol/sdk المثبت بالإصدار 1.32.1.

نُشر يوم 18 أكتوبر 2026 بالبناء `9IYPKydSlso_Xg6zzB066` للتطبيق والعامل، وكلاهما healthy. أُخذت نسخة احتياطية قبل المهاجرة، وطُبقت `0154` وسياسات RLS. نجح البناء وفحص TypeScript و98 اختباراً في 13 ملفاً؛ ونجح 31 فحص تكامل على قاعدة منفصلة، ثم تكررت الفحوص الـ31 عبر HTTP إلى حاوية الإنتاج التجريبية على Node 22.23.1. اجتاز الرابط الخارجي اكتشاف OAuth ورفض MCP دون تفويض وفحص الصحة وحماية صفحة الإعدادات، واجتازت نسخة التشغيل 5 فحوص API للهوية والصلاحيات. موافقة المستخدم في اختبار SDK كانت بمحاكاة مستخدم fixture؛ لم يُنشأ ربط تجريبي على بيانات الإنتاج ولم يُختبر دخول فعلي من حساب Claude أو ChatGPT.

## الاستخدام

عنوان الخادم في الإعداد الحالي: `https://app.sellerctrl.com/mcp`.

1. افتح إعدادات MCP أو الموصلات في عميل يدعم Streamable HTTP وOAuth، وأضف عنوان الخادم.
2. اختَر OAuth. الخادم يدعم التسجيل الديناميكي لعميل عام بـ`token_endpoint_auth_method=none`؛ لا تستخدم مفتاح الشركة القديم أو كلمة مرور ERP في إعدادات الموديل.
3. سجّل الدخول في SellerCtrl نفسه. راجع اسم التطبيق وعنوان الرجوع، واختَر الشركة والصلاحيات ثم وافق. اسم التطبيق يحدده العميل ولا يُعد توثيقاً لهويته.
4. المتاح فعلياً هو تقاطع اختيارك مع صلاحيات عضويتك الحالية وباقة الشركة. لا تتطلب أدوات القراءة صلاحيات ترحيل.
5. من `/settings/mcp` تستطيع رؤية روابط حسابك وآخر طلباتك وإلغاء ربط تطبيق واحد دون التأثير على الآخرين. الصفحة تتبع اللغة المختارة.

### واجهة الموافقة ونافذة إكمال الاتصال

نُشرت الواجهة يوم 18 أكتوبر 2026 بالبناء `TLCaW0rdiEPNxsQu2I1uN`. نجح البناء وTypeScript وESLint، و29 اختبار وحدة/تغطية لغة، و34 فحص تكامل OAuth والعزل، و14 فحص Chromium على الحاوية النهائية وقاعدة تجريبية. تشمل فحوص المتصفح فتح نافذة منفصلة بلا opener، نجاحًا بعد تبادل الرمز فقط، إبقاء صفحة SellerCtrl، حظر النوافذ، وإرسال النموذج الحقيقي بدون JavaScript. سياسة الإحالة `same-origin` تمنع تسريب عنوان الطلب للخارج وتسمح ببقاء Origin الصحيح لإرسال النموذج الأصلي، دون تخفيف حماية Server Actions.

شاشة `/mcp/authorize` مستقلة عن قائمة ERP، ببطاقة متجاوبة واختيار شركة وصلاحيات قابلة للتحديد وتفاصيل اتصال مطوية. تدعم RTL/LTR واللغة المختارة. أخطاء اختيار الشركة والتفويض تظهر داخل النموذج. اختيار صفر صلاحيات يعطل الموافقة، وتظل إمكانية الرفض متاحة.

تفتح الموافقة نافذة صغيرة من نقرة المستخدم مباشرة، مع فصل `opener` لحماية الصفحة الأصلية. يعيد إجراء الموافقة عنوان الرجوع المسجل نفسه، ويوجه إليه النافذة. تنتظر الصفحة الأصلية استهلاك رمز التفويض فعلياً، بفحص شخصي مقيد بالشركة والمستخدم وRLS ومعدل طلبات. عند نجاح التبادل تظهر رسالة نجاح SellerCtrl وإرشاد لإغلاق نافذة التأكيد؛ يُحاول إغلاقها لكن المتصفح قد يمنع الإغلاق عبر الأصل بعد فصل opener، لذلك لا يُضمن الإغلاق الآلي. لا تُعلن النجاح بمجرد إنشاء الرمز. لا تُرسل توكنات الوصول أو التجديد إلى صفحة الموافقة.

إذا منع المتصفح النافذة أو أغلقها المستخدم قبل التسليم، يُستخدم التحويل العادي إلى العنوان المسجل. بدون JavaScript يظل التحويل التقليدي يعمل. بعد دقيقتين بلا تأكيد تعرض الصفحة إرشاداً لإعادة البدء، دون ادعاء نجاح. صفحة callback المحلية لا تتغير؛ يملكها العميل مثل Codex، وتظهر في النافذة الصغيرة قبل إغلاقها. لا توجد موافقة تلقائية أو تجاوز لـPKCE.

`scripts/checks/chk-mcp-consent-ui.mjs` يختبر هذه الواجهة في Chromium حقيقي على قاعدة تجريبية فقط، ويحفظ صور سطح المكتب والموبايل في `.next/mcp-ui-preview`.

### استمرار تسجيل الدخول

نُشر إصلاح استمرار الدخول يوم 18 أكتوبر 2026 بالبناء `-5cwWFcDS7Wd1Nd9HJkx_` للتطبيق والعامل. نجح 21 اختباراً للتحويل وسياسات MCP، وفحص TypeScript وESLint والبناء. نجحت 4 فحوص تحويل فعلية على الحاوية المرشحة ثم تكررت عبر عنوان HTTPS الإنتاجي؛ الخدمة والعامل اجتازا فحص الصحة.

طلبات OAuth التي تصل إلى `/login?callbackUrl=…` يجب أن تعود إلى طلب الموافقة كاملاً حتى لو كان المستخدم مسجلاً بالفعل. يُستخدم `lib/auth/login-destination.ts` لقبول مسارات داخلية فقط ومنع الروابط الخارجية وحلقات تسجيل الدخول. يحتفظ دخول الإدارة ورابط تغيير الحساب في التحقق بخطوتين بوجهة الربط أيضاً. اختبارات `login-proxy.test.ts` تغطي التحويل الفعلي من proxy، واختبار `chk-live-login-continuation.ts` يتحقق من النسخة المنشورة دون إنشاء تفويض أو تغيير بيانات. عند استخدام Codex يُبدأ OAuth من العميل في المتصفح الخارجي؛ لا يحتاج المستخدم نسخ رابط من متصفح Codex المضمن. إذا انتهت مهلة عميل OAuth، يُبدأ طلب جديد من العميل بدلاً من إعادة استخدام الطلب القديم.

الربط ينتهي بعد 30 يوماً، وتوكن الوصول قصير العمر 10 دقائق مع تجديد دوّار. إعادة استخدام رمز تجديد مستهلك أو رمز تفويض مستهلك تلغي التفويض المرتبط به. إلغاء الجلسات أو إعادة تعيين كلمة المرور يبطل الوصول والتجديد عبر sessionVersion. تعطيل العضوية أو المستخدم وسحب الصلاحيات أو انتهاء الموديول تُفحص عند الطلب، وقبل تنفيذ كل أداة.

## الأدوات الحالية

| الأداة | الاستخدام |
|---|---|
| get_my_access | المستخدم والشركة المختارة والتفويض الحالي |
| search_items | بحث الأصناف بالكود والاسم وSKU وASIN والباركود، مع تقسيم صفحات |
| get_stock | رصيد صنف عبر المخازن أو مخزن معين، مع حجب التكلفة حسب التفويض والصلاحية |
| list_documents | أحدث 50 مستند بيع/شراء من الأنواع المسموحة؛ ليست كل السجلات التاريخية |
| get_document | تفاصيل أمر بيع/شراء أو استلام أو فاتورة بمعرف UUID |
| get_financial_report | الدخل والميزانية والتدفقات من الدفاتر الحالية بعملة الأساس |
| get_statement | كشف حساب أو عميل أو مورد داخل الشركة |
| get_marketplace_status | مفاتيح تشغيل المزامنة والترحيل وحالة المنصات، دون أسرار الاتصال |

تختلف قائمة الأدوات وأنواع المستندات حسب المستخدم والتفويض. لا توجد أدوات تعديل أو حذف أو SQL عام أو تشغيل مزامنة أو ترحيل أو عكس تسويات. نتائج القراءة تنقل بيانات دفاتر ERP الحالية، ولا تصحح تلقائياً أخطاء محاسبة تسويات أمازون التي وُثّقت في المراجعة السابقة.

صلاحيات التفويض: `erp.identity`, `inventory.read`, `purchases.read`, `sales.read`, `accounting.read`, `marketplace.read`.

لا تعني عبارة «لكل مستخدم» تخصيص مستندات الشركة لكل موظف: مشاركة بيانات الأعمال تتبع صلاحيات ERP الحالية. لكن الربط وسجل طلباته وإلغاؤه معزولة للمستخدم والشركة والتطبيق. قيود مخزن بعينه أو عملاء مندوب بعينه ليست ضمن هذا الإصدار.

## العزل والتشغيل

- الـaccess token مقيد بـissuer وaudience المحددين للخادم، ولا يُقبل توكن REST أو مفتاح شركة للدخول إلى MCP.
- تفويض واحد لشركة واحدة. معاملات الأدوات لا تتضمن سلطة تغيير userId أو orgId.
- جداول التفويض والأكواد والتجديد والتدقيق محمية بـRLS للشركة والمستخدم معاً. إجراءات إدارة الروابط تقيد الصفوف بالمستخدم أيضاً.
- سجل كل أداة يحمل المستخدم والتفويض ومعرف الطلب وحالته، دون نص المحادثة أو مدخلات حساسة أو التوكن الخام. الأكواد ورموز التجديد مخزنة كبصمات فقط.
- لا توجد جلسات SDK أو كاش نتائج مشترك بين المستخدمين. كل HTTP request ينشئ سيرفر محدوداً بتفويضه، وكل أداة تعيد فحصه.
- حدود: 64 KiB لجسم طلب MCP، و8 KiB لطلبات OAuth، و512 KiB للنتيجة قبل إرسالها. حد الاستعلام 10 ثوانٍ لكل statement، وحدود طلبات لكل مستخدم وتفويض وIP.
- يعتمد الإصدار على عملاء HTTP من الخادم أو تطبيقات تدعم OAuth؛ لا يقدم SSE قديماً أو STDIO أو وصول متصفح من أي Origin عشوائي. لم يُختبر داخل حساب فعلي لكل مزود موديل؛ جرى اختبار البروتوكول بعميل SDK الرسمي.

إعدادات الخادم: `APP_URL` هو الأصل الافتراضي، ويمكن تحديد `MCP_PUBLIC_URL` بعنوان HTTPS ينتهي بـ`/mcp`. لا يُشتق جمهور التوكن من Host المستخدم. `MCP_ENABLED=0` يوقف endpoint الأدوات. تعطيل الخدمة لا يغير بيانات ERP ولا يُفعّل أي مزامنة.

المهاجرة: `0154_mcp_personal_access`، ثم `npm run db:rls`. تحفظ سياسات RLS المخصصة للمستخدم في `db/rls/01-policies.sql` ولا تختفي مع إعادة تطبيق العزل. نسخة التطبيق السابقة لا تستخدم الجداول الجديدة، لذلك يمكن الرجوع للكود السابق مع إبقاء المهاجرة الإضافية.

## التحقق

دليل إعداد المستخدم للتطبيقات السبعة وإدارة التفويضات: [MCP_CLIENT_SETUP_AR.md](MCP_CLIENT_SETUP_AR.md).

اختبارات OAuth والتوكن وRLS والبروتوكول تعمل فقط على قاعدة اسمها يبدأ بـ`sellerctrl_mcp_test_`، مع حارس يرفض إنشاء fixtures خارجها. اختُبر بعميل SDK الرسمي: discovery، التسجيل الديناميكي، PKCE، تبادل الرمز والتجديد التلقائي، وقائمة الأدوات المقيدة. كما اختُبر فصل مستخدمين في شركة واحدة، منع إلغاء ربط الآخر، ومنع تبديل الشركة في مدخلات الأداة وإعادة استخدام الرموز.

`scripts/checks/chk-live-api-security.ts` فحص قراءة فقط للتطبيق المنشور؛ لا يطبع توكن الاختبار. الاختبارات لا تعادل اختبار اختراق شامل أو اعتماداً لتوافق جميع عملاء السوق.
