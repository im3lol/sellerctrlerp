# خطة تكافؤ SellerCtrl Mobile مع الموقع

## الهدف

تطبيق Android Native واحد يقدّم كل وظيفة متاحة للمستخدم على الموقع، بنفس:

- صلاحيات العضو داخل المؤسسة.
- الوحدات المشمولة في اشتراك المؤسسة.
- المنصات المتصلة والحالة الفعلية لها.
- دورة المستندات: مسودة → اعتماد → ترحيل، بدون تجاوز محرك المخزون أو المحاسبة.
- حالة الميزة: لا يظهر «قريبًا» إلا إذا كانت كذلك على الموقع بالفعل.

## قاعدة المصدر الواحد

| المصدر | المسؤولية |
| --- | --- |
| `components/app-shell/nav-config.ts` | أسماء الوحدات، المجموعات، وترتيب صفحات الموقع |
| `GET /api/v1/mobile-catalog` | القائمة الفعلية للمستخدم بعد الصلاحيات والاشتراك والمنصات |
| API الموبايل `/api/v1/**` | بيانات وعمليات التطبيق؛ Bearer token + `X-Org-Id` |
| تطبيق Android | تجربة الهاتف، التخزين الآمن، الكاميرا، والإشعارات |

لا تُنشأ قائمة يدوية ثانية داخل Android. كل صفحة تدخل الكتالوج بحالة واحدة من: `available` أو `coming_soon`، ولا تستخدم حالة افتراضية أو وهمية.

## المرحلة 0 — تثبيت الأساس والجودة

1. استبدال قائمة Android الموروثة بكتالوج `mobile-catalog`.
2. بناء قاموس مسارات: كل `href` من الموقع يقابله Route موبايل محدد واختبار يمنع المسارات غير المعالجة.
3. تخزين token والمؤسسة بشكل مشفّر باستخدام Android Keystore، مع تجديد/انتهاء جلسة واضح.
4. شاشة اختيار مؤسسة عند وجود أكثر من مؤسسة، وخروج آمن ومسح الجلسة.
5. معالجة offline / timeout / 401 / 403 / 404 برسائل عربية وإعادة المحاولة.

**معيار القبول:** لا يظهر عنصر غير مسموح به، ولا يوجد عنصر “قريبًا” بينما هو فعّال على الويب، ولا مسار موقع فعّال بلا Route موبايل أو سبب ظاهر ومقاس.

## المرحلة 1 — هيكل التجربة وواجهة الهاتف

1. App launcher مطابق للوحدات المفعّلة: المنصات، المحاسبة، المشتريات، المخزون، المبيعات، المستثمرون، HR، والتقارير.
2. تنقل سفلي للمهام اليومية: الرئيسية، البحث/الأصناف، المسح، الإشعارات/الموافقات، وكل التطبيقات.
3. بحث شامل من الهاتف للأصناف والعملاء والموردين والمستندات.
4. نظام تصميم موحّد: RTL، خط ثمانية، ألوان SellerCtrl، حالات loading/empty/error/success، ومساحات لمس لا تقل عن 44dp.
5. دعم الوضع الداكن وإتاحة الوصول: تباين، أحجام خط، قارئ الشاشة، ومحتوى لا يعتمد على اللون وحده.

**معيار القبول:** المستخدم يصل إلى أي عملية متاحة في ثلاث نقرات أو أقل من App launcher، ولا يوجد Sidebar مكتظ أو UI منسوخ من الديسكتوب.

## المرحلة 2 — Amazon والمنصات (أولوية الإطلاق)

1. صفحة المنصات: Amazon فعّالة، Noon وباقي المنصات “قريبًا” فقط حين تكون غير متاحة في الكتالوج.
2. Amazon hub: الصحة، المزامنة، آخر نتيجة، الأخطاء، الرسوم، الدفعات، الكشوف، وVerify.
3. Buy Box: قائمة المنتجات، السعر الحالي، المنافسة، التنبيهات، وفرز الحالات الحرجة.
4. FBA: الخطة، المخزون في Amazon مقابل النظام، الاقتراحات، حالة الشحنات، ومطابقة FBA.
5. التسويات: الاستيراد، النتائج، الفروقات، وربحية المنصة.
6. العمليات الحساسة تؤكد قبل التنفيذ وتعرض سجل النتيجة بدل تنفيذ صامت.

**معيار القبول:** مدير Amazon يستطيع متابعة اليوم التشغيلي من الهاتف: مزامنة، Buy Box، مخزون FBA، خطة إعادة التوريد، تسوية وفروقات.

### المنفّذ حاليًا

- مزامنة منفصلة للمنتجات، الأوامر، التسويات، وتدقيق FBA من الهاتف، مع حالة خلفية لكل عملية.
- مزامنة المنتجات تعتمد مسار المطابقة الحالي في النظام، الذي يجمع الـ SKU/FNSKU المختلفة تحت المنتج الأساسي بحسب ASIN.
- تدقيق FBA للقراءة والمقارنة فقط؛ إنشاء تسوية منه ينتج **مسودة** تتطلب مراجعة واعتمادًا صريحًا.
- استيراد التسويات لا يعني ترحيلًا محاسبيًا تلقائيًا من شاشة المزامنة؛ يبقى الترحيل خطوة مستقلة ومؤكدة.

## المرحلة 3 — المخزون والعمليات الميدانية

1. الأصناف: بحث، تفاصيل، ASIN وSKU وFNSKU تحت المنتج الأساسي، باركود وصور وأرصدة.
2. المخازن، الأرصدة، الحركة، المواقع، الأرقام التسلسلية، تقييم المخزون.
3. مسح الباركود: كاميرا، إدخال يدوي، نتيجة فورية، وإجراءات حسب صلاحية المستخدم.
4. التسويات، الجرد الدوري، التحويلات، الاستلام، الصرف، الحزم، الملصقات، جولات التجهيز وفحص الجودة.
5. التنبيهات: إعادة الطلب، راكد، صلاحية، ومطابقة FBA.

**معيار القبول:** أمين المخزن يستطيع إكمال الاستلام/التحويل/الجرد بالهاتف مع نفس قيود المخزون والاعتماد في الويب.

## المرحلة 4 — المبيعات والمشتريات

1. المبيعات: POS، عروض الأسعار، أوامر البيع، التسليم، الفواتير، المرتجعات، القبض، الفواتير الدورية.
2. العملاء: الملف، كشف الحساب، قوائم الأسعار، العروض والولاء، العمولات، تقارير العملاء والأصناف والربحية.
3. المشتريات: طلبات المواد، RFQ، أوامر الشراء، الاستلام، الفواتير، المرتجعات، الصرف، قراءة الفاتورة، وتكاليف الاستيراد.
4. الموردون: الملف، التقييم، دفتر المشتريات، GRNI، وخطة السداد.

**معيار القبول:** لا يُنشأ مستند موبايل خارج دورة مستندات النظام، وكل تأكيد/ترحيل يعرض أثره ويفشل بوضوح عند عدم امتلاك الصلاحية.

## المرحلة 5 — المحاسبة، المستثمرون والموارد البشرية

1. المحاسبة: الحسابات، القيود، الدفاتر، الكشوف، البنوك، المطابقة، المصروفات، العهد، الأصول، مراكز التكلفة، الفترات، الموازنة والتدفق النقدي.
2. المستثمرون: المستثمرون، المساهمات، توزيعات الأرباح، السحوبات.
3. HR: الموظفون، الحضور، الإجازات، المطالبات، الرواتب، العطلات، الأداء، التدريب والتوظيف حسب توفرها على الموقع.
4. الموافقات: صندوق موحّد للمستندات وطلبات HR حسب الدور.

**معيار القبول:** أي رقم مالي يراه المستخدم في الموبايل مصدره نفس محرك القيود والتقارير في الويب؛ لا حسابات محلية أو أرصدة مكررة.

## المرحلة 6 — التقارير، التصدير والطباعة

1. مركز تقارير موبايل: القوائم المالية، ضريبة القيمة، التدفق النقدي، التحليلات، النسب، العملات، مراكز التكلفة ولوحات المتابعة.
2. تصفية ثابتة للتاريخ، المؤسسة والمنصة مع حفظ آخر اختيار للمستخدم.
3. تصدير Excel/PDF عبر الخادم بنفس القوالب والأرقام، ومشاركة الملفات من الهاتف.
4. طباعة المستندات والتقارير عبر Android print/share بدون اختلاف في الهوية أو التفاصيل.

**معيار القبول:** ملف Excel أو PDF من التطبيق يطابق تقرير الويب لنفس الفترة والفلاتر، ويحتوي العناوين والأرقام والحالة بوضوح.

## المرحلة 7 — الإدارة والإعدادات والأمان

1. المؤسسة، المستخدمون والصلاحيات، الإعدادات، الترقيم، العملات، الأرصدة الافتتاحية، الطباعة، النسخ الاحتياطي وAPI keys بحسب الصلاحية.
2. سجل التدقيق، الإشعارات، Telegram/email status، والأتمتة إن كانت متاحة للمستخدم نفسه في الموقع.
3. حماية التطبيق: Keystore، منع لقطات الشاشة في الصفحات الحساسة، عدم طباعة token في logs، certificate pinning بعد تثبيت نطاق الإنتاج.
4. مراقبة أخطاء محلية قابلة للتصدير من داخل الإعدادات، بلا خدمات مدفوعة مفروضة.

**معيار القبول:** إعدادات المدير لا تظهر لغير المدير، ولا يمكن استخراج token أو بيانات مؤسسة أخرى من التخزين أو logs.

## المرحلة 8 — الاختبار والإطلاق

1. اختبارات Route parity: كل عنصر في الكتالوج له حالة ومسار موبايل مقصود.
2. اختبارات صلاحيات متعددة المؤسسات، انتهاء token، وحالات اشتراك منتهٍ/محدود.
3. اختبارات دورة شراء وبيع ومخزون ومحاسبة على بيانات تجريبية، ثم سيناريو Amazon/FBA فعلي غير مدمر.
4. اختبار أجهزة Android صغيرة وكبيرة، اتصال بطيء، كاميرا، RTL، الوضع الداكن وTalkBack.
5. توقيع Release، Play internal testing، سياسة خصوصية، أيقونات، screenshots، وخطة rollback.

**معيار الإطلاق:** لا توجد صفحة فعّالة على الويب غير معرّفة في الكتالوج أو بدون تجربة موبايل، ولا عملية ERP تتجاوز صلاحية أو محرك الترحيل، وAPK/AAB موقّع ومختبر.
